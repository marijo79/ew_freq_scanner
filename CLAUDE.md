# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

EW Frequency Scanner — a single configurable program (`src/freqscan/`) that drives an RTL-SDR and/or a HackRF to produce live spectrum + waterfall plots via matplotlib. Which SDR backend(s) run is chosen at startup by config, not by which script you invoke — both can run at once, sharing one plot window.

## Setup and running

```bash
python -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"

cp .env.example .env   # then fill in RTL__* and/or HACKRF__* — each section present is a backend that runs
python -m freqscan --plot   # requires rtl_power and/or hackrf_sweep on PATH + hardware attached, matching whichever sections are configured
                             # (--plot and/or --kafka_publisher — at least one is required, see Architecture item 5)

pytest -q
```

## Configuration

`src/freqscan/config.py` defines a `pydantic_settings.BaseSettings` (`Settings`), loaded from `.env` (see `.env.example`). There is no explicit backend selector — presence of the `RTL__*` / `HACKRF__*` nested section (using `__` as pydantic-settings' nested delimiter, e.g. `HACKRF__LNA_GAIN`) determines whether that backend runs; list fields (`RTL__DEVICES`, `HACKRF__RANGES`) are JSON-encoded strings deserialized into `DeviceConfig`/`RangeConfig` lists. A model validator enforces that at least one of the two sections is present. The `KAFKA__*` section (`KafkaSettings`) is fully optional and independent of that validator — its presence *and* its own `enabled` flag are necessary but not sufficient for streaming to run: unlike RTL/HackRF (config-only, no CLI gate), Kafka publishing also requires the `--kafka_publisher` CLI flag (`__main__.py`) on that specific run. `main()` nulls out `settings.kafka` before calling `build_backend()` if the flag wasn't passed, so `.env` having `KAFKA__*` configured never sends data anywhere by itself — it's a deliberate belt-and-suspenders: `.env` says streaming is *possible*, the flag says do it *this run*. Conversely, passing `--kafka_publisher` with no `KAFKA__*` section at all is a fast, explicit error (`main()` checks `settings.kafka is None` right after resolving the flag), not a silent no-op. `--plot` (open the plot window) and `--kafka_publisher` are independent and `parse_args()` requires at least one — `freqscan` refuses to run with neither, since that combination would just churn the SDR subprocesses with nothing ever reading the data. Kafka-only concerns like the signal-flagging margin (`signal_margin_db`, plus per-device/per-range overrides `rtl_margins_db`/`hackrf_margins_db` keyed by `DeviceConfig.id` / 0-based range index) live entirely inside `KafkaSettings`, not on `DeviceConfig`/`RangeConfig` — they're meaningless when Kafka isn't configured.

## Architecture

1. **Config → backend**: `sdr/build_backend(settings)` constructs an `RTLBackend` and/or `HackRFBackend` (`src/freqscan/sdr/{rtl,hackrf}.py`) for whichever sections are configured. If both are present, they're wrapped in a `CompositeBackend` (`sdr/base.py`) that runs them concurrently and concatenates their channel lists (RTL channels first) — `plotting.py`/`__main__.py` only ever see one `SDRBackend`, single or composite, so they're unaware of how many real backends are underneath. All three implement the `SDRBackend` ABC (`sdr/base.py`): a list of `Channel`s (one per plotted column), `start()`/`stop()`, and shared startup-failure tracking (`report_error()` / `wait_ready()`, see below).
2. **Producer thread(s)**: each backend launches the underlying SDR CLI tool (`rtl_power` or `hackrf_sweep`) as a subprocess and parses its CSV stdout line by line via the shared `parsing.parse_sweep_line()` (`hz_low, hz_step, ..., power, power, ...`). `RTLBackend` runs one subprocess/thread per configured device (1:1 with a channel); `HackRFBackend` runs a single subprocess covering all configured ranges in one sweep and demuxes each parsed line to the right channel by frequency (`_range_index_for`, which only checks a hop's *starting* frequency against each range's `[freq_start, freq_stop)`). Parsed `{freq_hz: power_dbm}` pairs are merged into each channel's `SweepState.sweep` dict, guarded by `SweepState.lock`. **After demuxing, `HackRFBackend._run()` also clips each hop's bins to the matched range's own `[freq_start, freq_stop)`** — necessary because `hackrf_sweep` has a hard minimum sweep segment width tied to its sample rate (~20MHz) and silently widens any narrower configured range to a full segment (e.g. requesting `106:107` actually sweeps `106-126`); without the clip, a hop's `hz_low` still matches the intended (narrow) range via `_range_index_for`, but the hop's *other* bins — genuinely from well outside that range — would leak into it. Found live 2026-08-10 configuring a 1MHz-wide range (106-107) for the first time; every prior range happened to be a clean multiple of the ~20MHz minimum, so this never came up before.
3. **Edge/roll-off handling differs by backend** — SDR filter roll-off makes the edge bins of every sweep hop unreliable, and each tool is handled with what it actually supports:
   - `RTLBackend` passes `rtl_power`'s own `-c <edge_trim*100>%` crop flag (recommended 20%-50%; see `rtl_power --help`). `rtl_power` widens each hop's capture window internally before cropping, so adjacent hops tile without gaps — do **not** re-add manual post-hoc trimming here, that was the original bug (created real frequency gaps because hops weren't widened to compensate).
   - `HackRFBackend` has no equivalent native flag, so it still uses `parsing.trim_edges()` to manually drop a fraction of bins from each edge of every hop (per-range `edge_trim`).
4. **Startup-failure detection**: `__main__.main()` calls `backend.start()`, then `backend.wait_ready(STARTUP_GRACE_PERIOD)` before opening any plot window. Each backend thread calls `self.report_error()` (sets a shared `threading.Event`) when its subprocess fails to launch (`OSError`, e.g. binary not on PATH) or exits with a positive return code (e.g. device not found) — `wait_ready()` returns `False` if that fired within the grace period, and `main()` stops the backend and exits(1) instead of opening a blank window.
5. **Consumer (main thread)**: `plotting.run()` builds a 2-row grid (spectrum on top, waterfall below), one column per channel, dark-themed via `style_axes()`, with `add_freq_hint()` wiring a mouse-move handler on the waterfall axes. `matplotlib.animation.FuncAnimation` polls channel states on a timer (`interval=200ms`) via `update_channel()`, which redraws the spectrum line and pushes into each channel's `deque(maxlen=waterfall_rows)` waterfall history — **each row stores its own `(freqs, powers)` arrays, not just `powers`**, and every redraw re-aligns each historical row onto the *current* frequency axis by value (`np.searchsorted`), not by column position. This matters whenever the known bin set (`state.sweep`'s keys) can change shape between frames — trivial/stable for RTL/HackRF (a full sweep covers every configured bin within the first hop or two) and, since item 7's metadata-driven pre-population, also stable for `KafkaConsumerBackend` from frame one. Aligning by column position instead of frequency value (the original, buggy approach, back when the Kafka viewer discovered its grid lazily and it kept growing for a while after startup) visibly shows as the whole waterfall shifting/compressing toward the low-frequency end for the first several seconds, as newly-discovered *lower* frequencies insert before already-known higher ones in the sorted column order — don't reintroduce that "simplification" even though the grid is stable now; it's still the only correct way to align a NaN-prepopulated grid against sparse real updates. **Fast path, added 2026-08-10**: once the grid *is* stable (true for almost every frame in practice), every row's own `freqs` array is identical to the current one — `update_channel()` checks that with `np.array_equal` first and does a plain positional copy (`mat[row, :] = row_powers`) instead of running `np.searchsorted` + masking, ~15x cheaper at tens of thousands of bins (measured: ~193ms → ~13ms per channel at 40,000 bins × 100 rows). Needed once `HACKRF__RANGES`' shared `bin_width` got fine enough (5kHz) that a wide range's bin count reached tens of thousands — at that scale the naive per-row realignment alone could exceed the 200ms redraw budget across multiple channels. Only runs when `--plot` was passed; without it, `main()` calls `run_headless()` instead (requires `--kafka_publisher`, since `parse_args()` rejects neither flag being set) — `SDRBackend.publisher` (set by `build_backend()` on whichever backend it returns, single or `CompositeBackend`, to the same shared `KafkaSignalPublisher` used internally) is polled every `OFFSET_REPORT_INTERVAL` (10s) via `KafkaSignalPublisher.offsets()` (per-partition last-delivered offset, tracked off every `produce()`'s delivery callback) and printed to stdout. `--plot` and `--kafka_publisher` are independent, so `--plot --kafka_publisher` together open the window *and* stream simultaneously.
6. **Kafka streaming (optional, `src/freqscan/streaming/`)**: if `settings.kafka` is present (i.e. `main()` didn't null it out for lack of `--kafka_publisher`, see Configuration above) and `kafka.enabled`, `build_backend()` constructs one shared `KafkaSignalPublisher` (`streaming/kafka_publisher.py`, wraps a `confluent_kafka.Producer` authenticated via SASL/IAM OAUTHBEARER using `aws-msk-iam-sasl-signer-python`) and — also in `build_backend()`, via `_build_rtl_detectors()`/`_build_hackrf_detectors()` — one `NoiseFloorDetector` per channel (`streaming/detector.py`), each seeded with that channel's `n_bins` (from a `ChannelGrid` computed once per channel by `_rtl_channel_grids()`/`_hackrf_channel_grids()` and reused for detector sizing, metadata publishing, *and* per-hop bin snapping, so all three always agree on the same layout) and margin (`kafka.rtl_margins_db`/`kafka.hackrf_margins_db` lookup, falling back to `kafka.signal_margin_db`). Backends themselves only ever receive already-built `publisher`/`detectors`/`canonical_freqs` and know nothing about `KafkaSettings`' shape. This is decoupled from the plotting/waterfall path entirely — it runs per-hop, directly in each backend's producer thread, right where `freqs`/`powers` for that hop are already computed and merged into `channel.state.sweep`.

   **`NoiseFloorDetector` is vectorized over a whole hop at once (`flag_hop(indices, powers)`), not called per-bin** — added 2026-08-16 after diagnosing a Raspberry Pi deployment pegging one CPU core at 100% with the producer backlogged (ping healthy, so not network-bound; confirmed compute-bound in the per-bin Python loop). Each channel's `n_bins`-wide rolling window (`KAFKA__BASELINE_WINDOW`, independent of `waterfall_rows`) is a circular-buffer 2D numpy array `(window, n_bins)` with per-bin `_fill_count`/`_cursor` arrays, replacing the old `dict[float, deque]`-per-bin design. Before calling `flag_hop`, each backend snaps the hop's real (possibly slightly off-grid) bin centers onto the channel's fixed grid via `nearest_grid_index(canonical_freqs, freqs)` (`np.searchsorted` + nearest-neighbor comparison) to get integer `indices` — real hardware's actual bin centers can differ from the nominal configured grid by sub-bin amounts, and `flag_hop` needs stable integer indices to index into its per-bin arrays. A bin only starts flagging once its own window has filled once (cold start, tracked per-bin via `_fill_count`). Measured ~9x faster than the old scalar per-bin loop at 20,000 bins/hop (realistic wide-HackRF-range scale): ~44ms → ~5ms.

   **Optional second, spatial check** (added to catch a whole band being uniformly noisy without treating that as N different signals — a single per-bin temporal baseline can't tell a genuinely elevated bin apart from a band that's just loud everywhere right now): if `spatial_margin_db` is configured (`kafka.rtl_spatial_margins_db`/`kafka.hackrf_spatial_margins_db` lookup, falling back to `kafka.spatial_margin_db`; `None` by default = disabled, pure temporal behavior), a temporally-flagged bin is only kept if it *also* beats that hop's median power (computed inside `flag_hop` itself via `np.median(powers)`, not by the caller) by that margin. It's an AND, not a replacement: spatial can only suppress an already-temporally-flagged bin, never flag one that failed the temporal check. **Optional third, prominence check** (added 2026-08-10, an OR alongside temporal rather than a refinement of it, unlike spatial): a signal that's always present and always strong — a steady FM broadcast carrier, say — trains straight into the temporal baseline and never looks "new" again no matter how strong it is, so temporal (and thus spatial, which only ever refines a temporal positive) never fires for it. If `prominence_margin_db` is configured (`kafka.rtl_prominence_margins_db`/`kafka.hackrf_prominence_margins_db` lookup, falling back to `kafka.prominence_margin_db`; `None` by default = disabled), a bin is flagged if it beats the hop's median by that margin **regardless of its own temporal history** — computed for bins not already flagged, so it's purely additive. Meant to use a bigger margin than `spatial_margin_db`, since a real narrowband peak clears a generous margin easily while generically noisy broadband bins (close to their own hop's median by definition) don't. All bins flagged within one hop are batched into a single JSON message (`streaming/kafka_publisher.build_payload()`) and published to one topic (`KAFKA__TOPIC`), keyed by channel label. **Partitioning is explicit, not left to Kafka's default key-hash partitioner**: `build_backend()` numbers every channel 0..N-1 in RTL-then-HackRF order (mirroring `CompositeBackend`'s channel-list ordering) and passes each backend a parallel `partitions: list[int]` — the exact same shape/indexing convention as `detectors` — which `RTLBackend`/`HackRFBackend` thread through to `KafkaSignalPublisher.publish(..., partition=...)`, guaranteeing each channel's messages land on one fixed partition rather than hoping the key hash spreads them out. The topic must be provisioned with at least as many partitions as total channels. If `settings.kafka` is absent or `kafka.enabled` is false, none of this runs — `build_backend()` passes `publisher=None`/`detectors=None`/`partitions=None`/`canonical_freqs=None` and the per-hop detector/publish calls are skipped entirely.

Both backends share parsing and plotting code — subprocess command construction, edge-trimming strategy, and channel demuxing differ.

7. **Kafka viewer (`python -m freqscan.kafka_viewer`, `src/freqscan/kafka_viewer.py`)**: a read-only consumer that draws the same spectrum+waterfall plot from the Kafka topic instead of live hardware — for watching signals on a machine with no SDR attached. `KafkaConsumerBackend` (`streaming/kafka_consumer.py`) implements the same `SDRBackend` ABC as `RTLBackend`/`HackRFBackend`, so `plotting.run()` needs no changes beyond item 5's alignment fix to draw from it. It uses `KafkaViewerSettings` (`config.py`), a small standalone settings class reading the same `KAFKA__*` `.env` vars as `KafkaSettings` but without going through `Settings`'/`_require_at_least_one_backend` (a viewer-only machine has no RTL/HackRF config at all).

   Channel layout comes from `KAFKA__METADATA_TOPIC` (default `freqscan.signals.metadata`), not from the signal messages: `build_backend()` (item 6) publishes one metadata message per channel, once at startup, on that channel's own partition — `{"channel", "freq_start_hz", "freq_stop_hz", "bin_width_hz", "n_bins", "run_epoch"}`, computed from static config (the same per-channel `ChannelGrid`s used for detector sizing, published via one shared `_publish_metadata()` in `sdr/__init__.py`; HackRF's `bin_width_hz` is `HackRFSettings.bin_width` — one value shared by every range, since `hackrf_sweep` only takes a single `-w` for its whole process; RTL's is per-device, `DeviceConfig.bin_width`). `KafkaConsumerBackend.__init__` blocks (up to `METADATA_TIMEOUT`, 10s, tracking per-partition `_PARTITION_EOF` to know when a partition has nothing more to offer) reading that topic from `OFFSET_BEGINNING` before doing anything else, printing `waiting for channel metadata...`/`got metadata for N channel(s)`.

   **`run_epoch` (`time.time()`, computed once per `build_backend()` call and reused for every channel's metadata message that run) exists because the metadata topic's partition count can only ever grow, never shrink** — once a topic has been provisioned/used for N channels, a later run with fewer channels (e.g. one HackRF range instead of three) still leaves the higher partitions holding their *previous* run's last message, since nothing ever deletes or compacts them. Deriving "how many channels this run has" from the broker's raw partition count (as an earlier version did) reads those stale leftover messages as real, live channels with old, wrong labels/extents — found live 2026-08-16 running with just 1 configured HackRF range against a locally over-provisioned 6-partition topic, and the viewer showed 6 channels with stale labels from an earlier, larger config. Fix: `KafkaConsumerBackend.__init__` reads metadata from every broker-reported partition as before, then keeps only the messages whose `run_epoch` equals the *maximum* `run_epoch` seen across all of them (exact equality, not a tolerance window — every message from one `build_backend()` call shares the identical value) — that's this run's live channel set, in contiguous partition order `0..n_channels-1`. A gap in that contiguous range (not all higher-numbered stale, but a genuine missing current-run partition) is `report_error()`, not a silent fallback. Only after this filtering does each channel's `state.sweep` get pre-populated with its **entire declared grid** (`np.linspace(freq_start_hz, freq_stop_hz, n_bins, endpoint=False)`) set to `NaN`, before the live signals consumer thread (seeked to `OFFSET_END`, as before) ever starts.

   This replaced an earlier "discover channels lazily from the first message per partition" design that had a real bug: since the signals topic only ever carries noise-floor-*flagged* bins (item 6), the known-bin set kept growing for a while after startup as new distinct frequencies got flagged for the first time — and because the waterfall's column positions depend on the *total* column count (item 5), that growth visibly reflowed the entire waterfall, not just new data, for a while after every startup. Publishing the true grid up front fixes this at the root instead of working around it in the rendering code.

   `apply_message()` merges a message's bins into `state.sweep` by **snapping each `freq_hz` to the nearest canonical grid frequency** (`nearest_grid_index()`, `np.searchsorted` + a nearest-neighbor comparison) rather than using it as a dict key directly — the producer's actual bin centers (parsed from `rtl_power`/`hackrf_sweep` output) and a grid computed from nominal config values can differ by sub-bin amounts, and without snapping that mismatch would silently add near-duplicate keys, reintroducing the exact growing-bin-count problem the metadata grid exists to avoid. Since metadata now provides labels/extents authoritatively before any real message arrives, `apply_message()` no longer does lazy label/extent discovery (a prior version did; removed as redundant, and it could have overwritten the correct full-range extent with a too-narrow one derived from just the first message's bins).

   Note the topic only carries noise-floor-*flagged* bins, so the viewer's spectrum/waterfall are inherently sparser than the producer's own local plot (which sees every raw bin) — this is expected, not a bug.

## Testing

`tests/test_parsing.py` and `tests/test_config.py` cover the two pure/testable layers: line parsing + edge trimming, and config loading/validation (including the no-backend-configured error, `metadata_topic` defaults/overrides, and `KafkaViewerSettings` loading independent of RTL/HackRF). `tests/test_sdr_build.py` covers `build_backend()` dispatch, `CompositeBackend` channel composition, and metadata-publish content (correct freq/bin_width/n_bins per channel, HackRF's single shared `bin_width`) — construction only, no subprocess/thread spawning (a shared `_FakeProducer` test double stands in for `confluent_kafka.Producer`; no real broker connection is ever created in tests). `tests/test_streaming_detector.py` and `tests/test_streaming_publisher.py` cover the other two pure layers: `NoiseFloorDetector.flag_hop()`'s cold-start/margin/spatial-AND/prominence-OR logic (array-based, plus `nearest_grid_index()`) and `build_payload()`/`build_metadata_payload()`'s message shapes. `tests/test_streaming_kafka_consumer.py` covers `nearest_grid_index()` and `apply_message()`'s snap-and-merge logic directly (no thread, no broker). Plotting/animation/thread glue and the actual Kafka I/O (`Producer.produce`/`flush`, `Consumer.poll`/`assign`, SASL/IAM token refresh) are intentionally not unit tested — matplotlib UI, thread orchestration, and a live broker aren't meaningfully testable without heavy mocking or real infrastructure.

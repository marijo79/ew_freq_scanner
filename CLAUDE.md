# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

EW Frequency Scanner — a single configurable program (`src/freqscan/`) that drives an RTL-SDR, a HackRF, and/or a PlutoSDR-compatible board to produce live spectrum + waterfall plots. Which SDR backend(s) run is chosen at startup by config, not by which script you invoke — any combination can run at once, sharing one plot window. Which *rendering library* draws that window (matplotlib or pyqtgraph) is a separate, independent config choice — see item 5.

## Setup and running

```bash
python -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"
# pip install -e ".[dev,plot-pyqtgraph]"   # add this extra too if you'll set PLOT_BACKEND=pyqtgraph (see item 5)

cp .env.example .env   # then fill in RTL__*, HACKRF__*, and/or PLUTO__* — each section present is a backend that runs
python -m freqscan --plot   # requires rtl_power and/or hackrf_sweep on PATH (Pluto's "tool", scripts/pluto_sweep.py, ships in this repo) + hardware attached, matching whichever sections are configured
                             # (--plot and/or --kafka_publisher — at least one is required, see Architecture item 5)

pytest -q
```

## Configuration

`src/freqscan/config.py` defines a `pydantic_settings.BaseSettings` (`Settings`), loaded from `.env` (see `.env.example`). There is no explicit backend selector — presence of the `RTL__*` / `HACKRF__*` / `PLUTO__*` nested section (using `__` as pydantic-settings' nested delimiter, e.g. `HACKRF__LNA_GAIN`) determines whether that backend runs; list fields (`RTL__DEVICES`, `HACKRF__RANGES`, `PLUTO__RANGES`) are JSON-encoded strings deserialized into `DeviceConfig`/`RangeConfig` lists (`RangeConfig` is shared by HackRF and Pluto — both single-device backends sweeping multiple configured ranges from one physical radio, unlike RTL's per-device `DeviceConfig`). A model validator enforces that at least one of the three sections is present. The `KAFKA__*` section (`KafkaSettings`) is fully optional and independent of that validator — its presence *and* its own `enabled` flag are necessary but not sufficient for streaming to run: unlike RTL/HackRF (config-only, no CLI gate), Kafka publishing also requires the `--kafka_publisher` CLI flag (`__main__.py`) on that specific run. `main()` nulls out `settings.kafka` before calling `build_backend()` if the flag wasn't passed, so `.env` having `KAFKA__*` configured never sends data anywhere by itself — it's a deliberate belt-and-suspenders: `.env` says streaming is *possible*, the flag says do it *this run*. Conversely, passing `--kafka_publisher` with no `KAFKA__*` section at all is a fast, explicit error (`main()` checks `settings.kafka is None` right after resolving the flag), not a silent no-op. `--plot` (open the plot window), `--kafka_publisher`, and `--csv DIR` (dump every raw sweep bin to one CSV file per channel in this directory, see item 5) are independent and `parse_args()` requires at least one of the three — `freqscan` refuses to run with none of them, since that combination would just churn the SDR subprocesses with nothing ever reading the data. Unlike Kafka, `--csv` has no `.env` counterpart to gate against — passing the flag is sufficient on its own. Kafka-only concerns like the signal-flagging margin (`signal_margin_db`, plus per-device/per-range overrides `rtl_margins_db`/`hackrf_margins_db`/`pluto_margins_db` keyed by `DeviceConfig.id` / 0-based range index) live entirely inside `KafkaSettings`, not on `DeviceConfig`/`RangeConfig` — they're meaningless when Kafka isn't configured.

`PlutoSettings` (PlutoSDR/AD9361-compatible boards) has no equivalent of `HACKRF__AMP_ENABLE` — checked against this project's own board's RF schematic (`AD936X_RF.SchDoc`): its TX/RX SMA connectors wire directly to the AD9361 through passive baluns only, no LNA/PA chip populated anywhere, so there's no discrete on/off amplifier to expose. The actual controllable RX gain path is `gain_control_mode` (`manual`/`fast_attack`/`slow_attack`/`hybrid`, AD9361's own AGC mode select) plus `hardwaregain` (dB, only sent to the device when `gain_control_mode` is `manual`) — set once at startup, not per-hop.

`PlutoStareSettings` (`PLUTO_STARE__*`) is Pluto's second, alternative mode: continuous single-frequency monitoring instead of sweeping (see item 2's "sweep vs. stare" note). **Mutually exclusive with `PlutoSettings`** — a model validator (`Settings._pluto_sweep_and_stare_are_mutually_exclusive`) rejects configuring both `PLUTO__*` and `PLUTO_STARE__*` at once, since they'd fight over the same exclusive-access physical radio; either is independently fine alongside RTL/HackRF. Its fields mirror `PlutoSettings`' naming where the concept is the same (`bin_width`, `gain_control_mode`, `hardwaregain`) but replace `ranges`/`capture_bandwidth` with a single `frequency` (MHz, the fixed RX LO) and `sample_rate` (Hz, the instantaneous bandwidth watched around it) — there's no list of ranges to sweep, just one fixed window.

## Architecture

1. **Config → backend**: `sdr/build_backend(settings)` constructs an `RTLBackend`, `HackRFBackend`, `PlutoBackend`, and/or `PlutoStareBackend` (`src/freqscan/sdr/{rtl,hackrf,pluto,pluto_stare}.py`) for whichever sections are configured — `pluto`/`pluto_stare` are mutually exclusive (see Configuration above) so at most one of that pair is ever built, taking the same "slot" in ordering below. If more than one backend is present, they're wrapped in a `CompositeBackend` (`sdr/base.py`) that runs them concurrently and concatenates their channel lists (RTL first, then HackRF, then Pluto/Pluto-stare) — `plotting.py`/`__main__.py` only ever see one `SDRBackend`, single or composite, so they're unaware of how many real backends are underneath. All four implement the `SDRBackend` ABC (`sdr/base.py`): a list of `Channel`s (one per plotted column — always exactly one for `PlutoStareBackend`, since there's only one fixed window), `start()`/`stop()`, and shared startup-failure tracking (`report_error()` / `wait_ready()`, see below). `HackRFBackend` and `PlutoBackend` share their channel-grid/detector-building logic (`_range_channel_grids()`/`_build_range_detectors()` in `sdr/__init__.py`) since both are single-device backends sweeping multiple configured `RangeConfig` ranges with one shared `bin_width` — RTL's per-device grid/detector building stays separate since each RTL device gets its own `bin_width`, and `PlutoStareBackend`'s single-channel grid/detector building (`_pluto_stare_channel_grid()`) stays separate too since there's no `ranges` list or per-index margin overrides to share the pattern with — it just falls back to `KafkaSettings`' plain `signal_margin_db`/`spatial_margin_db`/`prominence_margin_db`.
2. **Producer thread(s)**: each backend launches the underlying SDR CLI tool (`rtl_power`, `hackrf_sweep`, or — for Pluto — this repo's own `scripts/pluto_sweep.py`) as a subprocess and parses its CSV stdout line by line via the shared `parsing.parse_sweep_line()` (`hz_low, hz_step, ..., power, power, ...`). `RTLBackend` runs one subprocess/thread per configured device (1:1 with a channel); `HackRFBackend` and `PlutoBackend` each run a single subprocess covering all configured ranges in one sweep and demux each parsed line to the right channel by frequency (`_range_index_for`, which only checks a hop's *starting* frequency against each range's `[freq_start, freq_stop)`). Parsed `{freq_hz: power_dbm}` pairs are merged into each channel's `SweepState.sweep` dict, guarded by `SweepState.lock`. **After demuxing, both `HackRFBackend._run()` and `PlutoBackend._run()` also clip each hop's bins to the matched range's own `[freq_start, freq_stop)`** — necessary because `hackrf_sweep` has a hard minimum sweep segment width tied to its sample rate (~20MHz) and silently widens any narrower configured range to a full segment (e.g. requesting `106:107` actually sweeps `106-126`), and `pluto_sweep.py`'s own widen-then-crop hop tiling (item 3 below) can likewise overshoot a range's configured `freq_stop` by up to one retained step on the last hop; without the clip, a hop's `hz_low` still matches the intended (narrow) range via `_range_index_for`, but the hop's *other* bins — genuinely from outside that range — would leak into it. Found live 2026-08-10 configuring a 1MHz-wide HackRF range (106-107) for the first time; every prior range happened to be a clean multiple of the ~20MHz minimum, so this never came up before.
3. **Edge/roll-off handling differs by backend** — SDR filter roll-off makes the edge bins of every sweep hop unreliable, and each tool is handled with what it actually supports:
   - `RTLBackend` passes `rtl_power`'s own `-c <edge_trim*100>%` crop flag (recommended 20%-50%; see `rtl_power --help`). `rtl_power` widens each hop's capture window internally before cropping, so adjacent hops tile without gaps — do **not** re-add manual post-hoc trimming here, that was the original bug (created real frequency gaps because hops weren't widened to compensate).
   - `HackRFBackend` has no equivalent native flag, so it still uses `parsing.trim_edges()` to manually drop a fraction of bins from each edge of every hop (per-range `edge_trim`).
   - `scripts/pluto_sweep.py` (Pluto's "native tool", see item 2) implements the same widen-then-crop approach as `rtl_power` itself, internally: for each hop it captures a wider span than its nominal step (`--capture-bandwidth`, up to the AD9361's ~56MHz hardware max) and calls `parsing.trim_edges()` *inside the script* before ever printing a CSV line — so, like `RTLBackend`, `PlutoBackend` does **not** call `trim_edges()` again itself; the CSV it parses is already cropped. The retained (post-crop) step between hop centers is `capture_bandwidth * (1 - 2*edge_trim)`, computed per-range from that range's own `edge_trim`, exactly mirroring how `RangeConfig.edge_trim` already works for HackRF.

   **`scripts/pluto_sweep.py` itself** exists because, unlike RTL-SDR/HackRF, there's no ADI-native `rtl_power`-equivalent sweep CLI — checked live 2026-09-03: `pyadi-iio`'s own examples have no sweep/CSV-output helper, and ADI's official "IIO Oscilloscope"/Scopy GUI tools have no headless/batch mode at all, so nothing off-the-shelf fit this repo's "spawn a CLI, parse its CSV" architecture. It drives the hardware via the same two `libiio` CLI tools used to verify this by hand (`iio_attr` to retune the RX LO per hop and to set `sampling_frequency`/`rf_bandwidth`/`gain_control_mode`/`hardwaregain` once at startup; `iio_readdev` to capture each hop's raw `int16` I/Q buffer from the `cf-ad9361-lpc` device's `voltage0`/`voltage1` channels), then does the FFT itself in Python (`numpy`, Hanning-windowed). One process handles every configured `--range` in turn from a single persistent connection (`--repeat` loops the whole set) — deliberately unlike RTL's one-subprocess-per-device model, since Pluto (like HackRF) is one exclusive-access physical radio and two sweep processes can't retune/capture against it concurrently. Both `pluto_sweep.py` and `pluto_stare.py` (below) validate up front that `bin_width` isn't too coarse relative to their capture width — `trim_edges()` drops `max(1, int(n_bins * edge_trim))` bins from each side, and with too few bins per capture to begin with (e.g. `bin_width` close to or exceeding the capture bandwidth), trimming can eat the *entire* capture, leaving `trim_edges()` nothing to return and crashing with an `IndexError` instead of a clear error — found live 2026-09-03 configuring a 50MHz `bin_width` against a 20MHz `capture_bandwidth` while exploring "how coarse can bins usefully get."

   **`scripts/pluto_stare.py`** is Pluto's second mode: instead of hopping across ranges, it retunes the RX LO **once** at startup and stays there — the "stare" counterpart to "sweep." The tradeoff (SIGINT/ESM's classic "sweep vs. stare"): sweeping N hops means looking at any one frequency only ~1/N of the time, missing brief or intermittent signals that happen to occur on a different hop; staring at one fixed frequency continuously catches everything there and allows much longer effective averaging (better SNR for a weak signal), at the total cost of zero visibility into the rest of the spectrum meanwhile. Mechanically, this rules out `pluto_sweep.py`'s per-hop `iio_readdev` restart (there's no retuning between captures to justify it) — instead, `iio_readdev` is launched **once**, with `-s 0` (0 = infinite, streams forever instead of exiting after one buffer), and the script just keeps reading fixed-size chunks from that one already-running subprocess's stdout in a loop, FFTing each chunk. Measured live 2026-09-03: ~424 FFT windows/sec this way at 4096 bins, versus roughly one hop/sec from `pluto_sweep.py`'s restart-per-capture design — confirming the restart overhead, not the FFT itself, dominates `pluto_sweep.py`'s pacing. Still applies `edge_trim`/`trim_edges()` to drop unreliable roll-off bins at the edges of each capture, same as `pluto_sweep.py` — but here purely for capture-edge quality, not to tile adjacent hops without gaps (there's only ever one window, nothing to tile against).

   **One `iio_readdev` connection captures every configured RX channel together, not one connection per channel** — rewritten 2026-09-04 chasing a real throughput bottleneck. The original design ran one `pluto_stare.py` instance per `PlutoStareSettings.channels` entry, each independently connecting and streaming; this worked over the `ip:` backend (Pluto's onboard IIOD network daemon multiplexes concurrent client connections itself) but already measurably throttled each channel (observed ~18-20 lines/sec for a lone channel dropping to as low as ~2.5 lines/sec for the second one running concurrently, both at 20MHz `sample_rate`). Trying to fix that by switching to libiio's `usb:` backend (direct USB bulk transfer, no network stack in the way — confirmed faster: ~22MB/s vs ~16.5MB/s sustained for the same 2-channel capture) exposed a hard incompatibility: `usb:` claims the USB interface **exclusively**, so a second process's own `usb:` connection to the same device fails outright (`Unable to claim interface: Device or resource busy`) the instant the first is already streaming — confirmed live by racing two concurrent `iio_attr` calls against `usb:1.82.5`. Since only one process may ever hold the `usb:` connection at a time, capturing 2 RX channels over `usb:` requires that *one* process read both channels' I/Q from *one* buffer. `iio_readdev` supports this natively: requesting multiple channels on its command line (e.g. `cf-ad9361-lpc voltage0 voltage1 voltage2 voltage3` for both RX1 and RX2) interleaves them per-sample-time in the exact order given — confirmed live by capturing a few raw samples across all 4 sub-channels and inspecting the bytes directly (`iio_readdev -b 256 -s 3 cf-ad9361-lpc voltage0 voltage1 voltage2 voltage3` in this repo's own tests, verifying (I1,Q1,I2,Q2) repeats in order). `stare()` now reshapes the flat interleaved buffer to `(n_bins, 2 * n_channels)` and slices out each channel's own I/Q columns, FFTs each independently, and prints one CSV line per configured channel per capture — each line prefixed with its RX channel number as a leading field (`channel, date, time, hz_low, ...`) so `PlutoStareBackend`'s single reader thread can demux lines back to the right `Channel`/detector/csv writer; the leading tag is stripped before the remainder ever reaches `parsing.parse_sweep_line()`, so that shared parser (also used by RTL/HackRF/`pluto_sweep.py`) needed no changes at all. `--channel-configs` (a JSON list, same shape as `.env`'s `PLUTO_STARE__CHANNELS`) replaced the old singular `--channel`/`--gain-control-mode`/`--hardwaregain` flags to carry every configured channel's own gain settings into the one process. `PlutoStareBackend` mirrors this: `start()`/`_run()` spawn exactly one subprocess regardless of channel count (down from one per channel), and `PlutoStareSettings.uri` (`PLUTO_STARE__URI`) stays a plain, fully general config value either way — nothing hardcodes `ip:` or `usb:`, so falling back to `ip:` (e.g. on a machine without direct USB access) is still just a one-line `.env` edit. **Use the bare `usb:` form, not a specific `usb:x.y.z` address** — found live 2026-09-04 that a specific address breaks on reconnect: a Pluto physically unplugged/replugged mid-session came back at a different USB enumeration (`usb:1.82.5` → `usb:1.86.5`, confirmed via `iio_info -s` showing the same device serial at a new address), and `PLUTO_STARE__URI=usb:1.82.5` then failed to resolve at all. libiio's `-u usb:` (documented in `iio_readdev --help`'s own usage examples, alongside the specific-address form) auto-resolves a bare `usb:` to whichever single USB context is currently connected, sidestepping the whole problem — confirmed working live. Only ambiguous if more than one PlutoSDR-compatible device is connected at once, in which case a specific `usb:x.y.z` (from `iio_info -s`) is still needed.

   **The real per-line cost is Python-side FFT + string-formatting CPU time, which scales with `n_bins` (= `sample_rate / bin_width`) — not raw USB/network bandwidth, which sits far below its own ceiling across this whole practical range.** This was confirmed as the true root cause of a "waterfall shows persistent vertical lines" symptom reported live 2026-09-04: `plotting/common.py`'s `channel_snapshot()` was (correctly, per its own fix — see item 5) skipping duplicate frames, which then made the *real* problem visible as long flat/empty stretches — a live measurement found 92 of 99 consecutive display-tick reads returning pixel-for-pixel identical `state.sweep` data, meaning the producer was updating at only ~1.6Hz against the display's 20Hz/50ms refresh. That measurement was taken *before* the shared-connection fix above, with the old one-process-per-channel design fighting over one link — misleadingly, a follow-up raw-`dd` bandwidth probe (no FFT, just piping `iio_readdev`'s output to `/dev/null`) measured only ~22MB/s sustained over `usb:` for a 2-channel capture, which looked like a hard link ceiling and led to `sample_rate` initially being cut all the way down to `2083334` (the AD9361's own hardware-enforced minimum sampling_frequency; confirmed live that `2000000` is rejected outright by `iio_attr` with "Invalid argument") to fit under it. **That conclusion was wrong** — measuring the actual `pluto_stare.py` reader loop's real sustained line rate directly (not inferred from duplicate-frame counting, and not from a no-FFT `dd` probe) shows it uses nowhere near that ~22MB/s ceiling at any practical `bin_width`/`sample_rate` combination: e.g. at the original `PLUTO_STARE__SAMPLE_RATE=50000000`/`PLUTO_STARE__BIN_WIDTH=25000` (`n_bins` ≈ 2000, matching the config's own long-standing comment that bin_width was deliberately scaled up alongside sample_rate specifically to keep `n_bins` roughly fixed), real measured throughput for *both* RX channels together is ~214 lines/sec each — over 10x the display's 20Hz need — because the actual bytes moved per second at that `n_bins` (`lines/sec * n_bins * 4 bytes`) is only a few MB/s, far under the ~22MB/s the link can carry; the FFT+formatting work per line is what limits `lines/sec`, and that cost tracks `n_bins`, not `sample_rate` directly. Doubling (or more) `sample_rate` while holding `bin_width` proportionally higher — exactly what the original 50MHz config already did — keeps `n_bins` and therefore real throughput about the same. Net result: once both RX channels share one connection (the fix above), `PLUTO_STARE__SAMPLE_RATE=50000000` (near Pluto's ~56MHz hardware max, covering most of the WiFi 2.4GHz band) is fully real-time for 2 channels and needs no reduction at all — confirmed live back at the original config, 0 duplicate frames, ~214 lines/sec measured per channel. `PLUTO_STARE__BIN_WIDTH` is still the one knob that actually matters for throughput: raising it (fewer, coarser bins) speeds up the per-line CPU cost, lowering it (more, finer bins) slows it down, regardless of `sample_rate`.

   **`sample_rate` is capped at Pluto's own ~56MHz hardware max regardless of any of the above** — going wider than one AD9361 instantaneous capture needs sweep mode's multi-range hopping (`PlutoBackend`, item 1/2) instead; stare mode is fundamentally limited to one fixed window. So once `sample_rate` is already near that ceiling (50MHz), the only remaining lever for using the spare CPU/link headroom found above is `PLUTO_STARE__BIN_WIDTH` — finer resolution (more bins) within the same fixed span, not wider coverage. Measured live 2026-09-04 at `sample_rate=50_000_000`, varying `bin_width` alone: `n_bins * lines/sec` stays roughly constant (~420,000) across the practical range (`bin_width=25000` → `n_bins=2000` → ~222 lines/sec; `12500`→4000→~116; `10000`→5000→~104 sustained over 15s; `8000`→6250→~74; `6250`→8000→~56; `5000`→10000→~39; `2500`→20000→~19.6 — right at the display's 20Hz need with no safety margin left, confirming the relationship holds all the way down). Moved from the original `25000` to `10000` (2.5x finer resolution) for a comfortable ~5x margin over the display's ~20Hz refresh; going below ~8000-10000 here starts eating into that margin and should be re-measured before changing.
4. **Startup-failure detection**: `__main__.main()` calls `backend.start()`, then `backend.wait_ready(STARTUP_GRACE_PERIOD)` before opening any plot window. Each backend thread calls `self.report_error()` (sets a shared `threading.Event`) when its subprocess fails to launch (`OSError`, e.g. binary not on PATH) or exits with a positive return code (e.g. device not found) — `wait_ready()` returns `False` if that fired within the grace period, and `main()` stops the backend and exits(1) instead of opening a blank window.
5. **Consumer (main thread)**: `plotting/` is a package, not a single module, because there are two independent, interchangeable rendering implementations behind one dispatcher — `plotting/__init__.py`'s `run(backend, waterfall_rows, refresh_ms, plot_backend)` lazily imports and delegates to either `plotting/matplotlib_backend.py` (default) or `plotting/pyqtgraph_backend.py` based on `settings.plot_backend` (`PLOT_BACKEND` in `.env`, `Literal["matplotlib", "pyqtgraph"]`, default `"matplotlib"`) — the lazy import means picking matplotlib never requires pyqtgraph to be installed. This was an explicit product decision, not a migration: pyqtgraph was added *alongside* matplotlib as a config-switchable alternative because matplotlib's per-subplot blit overhead (measured live 2026-09 at ~150-285ms/frame once several channels are active) becomes a real bottleneck exactly where `PlutoStareSettings` (item 2) wants to show hundreds of FFT windows/sec — never as a wholesale replacement. Both implementations share one data-prep module, `plotting/common.py`: `channel_snapshot(channel, waterfall_rows)` builds one channel's current frame (`mhz`, `powers`, `waterfall_matrix`) from `channel.state.sweep`/`channel.state.history` and is the *only* place a frame gets recorded into history, and `initial_ylim(channel)` peeks at a channel's first real data to pick a tightly-fitted, fixed y-range up front (both backends fix axis limits rather than auto-ranging every frame — required for matplotlib's `blit=True`, and genuine avoidable per-frame cost in pyqtgraph too). **`initial_ylim()`/`initial_waterfall_clim()` filter out `NaN` before checking whether any real data has arrived** — a plain "is `state.sweep` non-empty" check isn't enough, since `KafkaConsumerBackend` (item 7) pre-populates every declared grid bin with `NaN` at construction, so that check would pass immediately with zero real (flagged) values yet received; found live 2026-09-20 running `kafka_viewer` end-to-end for the first time against a real sparse topic — `min()`/`max()`/`percentile()` over an all-`NaN` list is `NaN`, which crashed pyqtgraph's `setYRange(nan, nan)` outright instead of waiting/falling back to `FALLBACK_SPECTRUM_YLIM` like these functions are meant to. A no-op for every other backend, whose `state.sweep` only ever holds real values once a hop actually lands. Putting this logic in one shared module rather than duplicating it per backend is what keeps the rolling-waterfall-history alignment behavior (below) identical in both — a bug or a fix here can't accidentally diverge between them. **`channel_snapshot()` skips appending a history row when the frame is pixel-for-pixel identical to the last one recorded** — found live 2026-09-04 running 2 concurrent `PlutoStareSettings` channels (see item 2/3's docstring on `PlutoStareBackend`: both RX streams share one USB/IP link to the device, and running two at once was already documented to throttle one channel's real update rate down to as low as ~2.5 lines/sec). Since the display redraws on its own fixed `plot_refresh_ms` timer regardless of whether the producer has actually written anything new, a producer slower than the display previously got its one real capture appended as a "new" row on every single redraw tick until fresh data arrived — measured live at 92 of 99 consecutive display ticks reading back-to-back identical `state.sweep` snapshots — stretching one real capture across dozens of waterfall rows and rendering as static-looking vertical bands that misrepresented how much independent temporal data actually existed. The fix compares each new frame's `freqs`/`powers` against `state.history[-1]` and only appends on a genuine change, so a slow producer now just makes the waterfall scroll slower (fewer, but real, rows) instead of duplicating its last frame.

   **`matplotlib_backend.py`** builds a 2-row grid (spectrum on top, waterfall below), one column per channel, dark-themed via `style_axes()`, with `add_freq_hint()` wiring a mouse-move handler on the waterfall axes. `matplotlib.animation.FuncAnimation` polls channel states on a timer (`interval=settings.plot_refresh_ms`, `PLOT_REFRESH_MS` in `.env`, default 200ms) via `update_channel()`, which calls `channel_snapshot()` and redraws the spectrum line and waterfall image from its result. `channel_snapshot()`'s `waterfall_matrix` is built from `channel.state.history` (a `deque(maxlen=waterfall_rows)`, populated by `channel_snapshot()` itself) — **each row stores its own `(freqs, powers)` arrays, not just `powers`**, and every redraw re-aligns each historical row onto the *current* frequency axis by value (`np.searchsorted`), not by column position. This matters whenever the known bin set (`state.sweep`'s keys) can change shape between frames — trivial/stable for RTL/HackRF (a full sweep covers every configured bin within the first hop or two) and, since item 7's metadata-driven pre-population, also stable for `KafkaConsumerBackend` from frame one. Aligning by column position instead of frequency value (the original, buggy approach, back when the Kafka viewer discovered its grid lazily and it kept growing for a while after startup) visibly shows as the whole waterfall shifting/compressing toward the low-frequency end for the first several seconds, as newly-discovered *lower* frequencies insert before already-known higher ones in the sorted column order — don't reintroduce that "simplification" even though the grid is stable now; it's still the only correct way to align a NaN-prepopulated grid against sparse real updates. **Fast path, added 2026-08-10**: once the grid *is* stable (true for almost every frame in practice), every row's own `freqs` array is identical to the current one — `channel_snapshot()` checks that with `np.array_equal` first and does a plain positional copy (`mat[row, :] = row_powers`) instead of running `np.searchsorted` + masking, ~15x cheaper at tens of thousands of bins (measured: ~193ms → ~13ms per channel at 40,000 bins × 100 rows). Needed once `HACKRF__RANGES`' shared `bin_width` got fine enough (5kHz) that a wide range's bin count reached tens of thousands — at that scale the naive per-row realignment alone could exceed the 200ms redraw budget across multiple channels.

   **`pyqtgraph_backend.py`** builds the same 2-row-per-channel layout in a `pg.GraphicsLayoutWidget`, using `PlotItem.plot()` for the spectrum curve and a `pg.ImageItem` (inferno colormap via `pg.colormap.get("inferno").getLookupTable()`) for the waterfall, updated on a `QtCore.QTimer` (no `FuncAnimation` equivalent) at the same `refresh_ms`. Its own `_add_freq_hint()` reimplements the hover crosshair with an `InfiniteLine` + `TextItem` reacting to the shared `GraphicsLayoutWidget` scene's `sigMouseMoved` signal — pyqtgraph has no blit/full-redraw split, so there's no equivalent of matplotlib's `animated=True` workaround needed there. **`pg.ImageItem.setImage()` silently resets both the item's lookup table and its coordinate rect on every call** — confirmed live 2026-09-04 debugging the waterfall rendering as a flat solid color despite `channel_snapshot()`'s data being verified correct (dumped the exact real array and reproduced the bug in isolation): a one-time `setLookupTable()`/`setRect()` at setup time only survives until the *first* real `setImage()` call in the update loop, after which the LUT and rect silently fall back to defaults (rect resets to raw pixel dimensions `(0, 0, n_cols, waterfall_rows)`, completely outside the fixed MHz/row view range set once at startup — the image was being drawn entirely off-screen from the visible viewport's perspective, which one might expect to render as blank rather than a solid color, but didn't). Fix: pass `lut=lut` and `rect=<QRectF>` directly as kwargs on *every* `setImage()` call (both are accepted via `ImageItem.setOpts`, which `setImage()` forwards `**kwargs` to) rather than relying on a setup-time call to either method.

   Both backends: `plot_refresh_ms` is one setting for the whole window (one shared timer/animation redraws every channel together each tick) — there's no way to redraw one channel's plot faster than another's without a bigger redesign. This matters for `PlutoStareSettings` (`pluto_stare.py`, item 2): it can produce hundreds of FFT windows/sec, but at the default 200ms refresh, `channel_snapshot()` only ever sees whichever single window happened to be the latest in `channel.state.sweep` at each 5Hz tick — nearly all of that throughput gets overwritten and never reaches the screen unless `PLOT_REFRESH_MS` is lowered (e.g. to 50). Only runs when `--plot` was passed; without it, `main()` calls `run_headless()` instead — `SDRBackend.publisher` (set by `build_backend()` on whichever backend it returns, single or `CompositeBackend`, to the same shared `KafkaSignalPublisher` used internally) is polled every `OFFSET_REPORT_INTERVAL` (10s) via `KafkaSignalPublisher.offsets()` (per-partition last-delivered offset, tracked off every `produce()`'s delivery callback) and printed to stdout — only when `--kafka_publisher` was actually passed (`backend.publisher` is `None` otherwise, e.g. a `--csv`-only headless run, in which case `run_headless()` just idles silently until Ctrl-C). `--plot`, `--kafka_publisher`, and `--csv` are all independent and freely combinable, so e.g. `--plot --kafka_publisher --csv out.csv` opens the window, streams to Kafka, *and* dumps to disk simultaneously.

   **Raw CSV dump (`--csv DIR`, `src/freqscan/csv_writer.py`)**: one `CsvSweepWriter` **per channel**, not one shared file — device/frequency-range identity lives in the filename, not in the row data, so each file only needs `timestamp,freq_hz,power_dbm`. `build_backend()` builds a `list[CsvSweepWriter]` parallel to each backend's channels (the same shared-list-per-channel shape as `detectors`/`partitions`) via `make_csv_path(csv_dir, device, freq_start_mhz, freq_stop_mhz, when)`, where `device` is `f"RTL-Dev{dev.id}"` per RTL device or the literal `"HackRF"` per range, and `freq_start_mhz`/`freq_stop_mhz` come from that channel's already-computed `ChannelGrid` (same grids used for detector sizing/metadata). `when` is one `datetime.now()` captured once per `build_backend()` call (mirroring `run_epoch`'s one-timestamp-per-run pattern) so every file from one run shares the same trailing timestamp and sorts/groups together, rather than drifting by the few seconds each channel takes to start. `csv_dir` is created via `os.makedirs(exist_ok=True)` if missing. Each backend calls `csv_writer.write_hop(freqs, powers)` (now 2-arg, no channel label) right where it already has that hop's post-trim `freqs`/`powers` — same location as the Kafka publish call, but logging *every* bin of every hop, not just noise-floor-flagged ones (unbounded row volume by design — measured ~500k rows in ~5s / a ~20MB file at `HACKRF__BIN_WIDTH=25000` over a single 100MHz range; pick bin width/range width with that in mind, see item 2's Pi CPU bottleneck for what happens when per-hop Python work outgrows the sweep rate). Each file is opened once in `'w'` mode (truncates on every run, not append) with its header row written immediately, so a run that fails at startup (see item 4) still leaves valid header-only CSVs, not partial/corrupt ones. Closed via `writer.close()` per channel in each backend's `stop()`, mirroring the existing `publisher.flush()` call there.
6. **Kafka streaming (optional, `src/freqscan/streaming/`)**: if `settings.kafka` is present (i.e. `main()` didn't null it out for lack of `--kafka_publisher`, see Configuration above) and `kafka.enabled`, `build_backend()` constructs one shared `KafkaSignalPublisher` (`streaming/kafka_publisher.py`, wraps a `confluent_kafka.Producer`) and — also in `build_backend()`, via `_build_rtl_detectors()` (RTL) or the shared `_build_range_detectors()` (HackRF and Pluto, see item 1) — one `NoiseFloorDetector` per channel (`streaming/detector.py`), each seeded with that channel's `n_bins` (from a `ChannelGrid` computed once per channel by `_rtl_channel_grids()`/`_range_channel_grids()` and reused for detector sizing, metadata publishing, *and* per-hop bin snapping, so all three always agree on the same layout) and margin (`kafka.rtl_margins_db`/`kafka.hackrf_margins_db`/`kafka.pluto_margins_db` lookup, falling back to `kafka.signal_margin_db`). Backends themselves only ever receive already-built `publisher`/`detectors`/`canonical_freqs` and know nothing about `KafkaSettings`' shape. This is decoupled from the plotting/waterfall path entirely — it runs per-hop, directly in each backend's producer thread, right where `freqs`/`powers` for that hop are already computed and merged into `channel.state.sweep`.

   **Client auth/TLS config is built by one shared `build_client_config()`** (`kafka_publisher.py`, duck-typed against either `KafkaSettings` or `KafkaViewerSettings` — both carry the same connection fields independently, see `KafkaViewerSettings`' own docstring on why they're separate classes — and reused by `kafka_consumer.py`'s `build_consumer()` for the read-only viewer). Real MSK's default `security_protocol="SASL_SSL"`/`sasl_mechanism="OAUTHBEARER"` signs its own short-lived token per connection via `oauth_cb()` (`aws-msk-iam-sasl-signer-python`), ignoring `sasl_username`/`sasl_password` entirely. Added 2026-09-20 for a self-hosted broker with no AWS credentials involved (e.g. the `pi-remote-access` tunnel VM's broker, publicly reachable so a field Pi can reach it with no LAN path to a local broker): `sasl_mechanism="SCRAM-SHA-512"` (or `PLAIN`) uses `sasl_username`/`sasl_password` directly instead, and `ssl_ca_location` pins a self-signed broker TLS cert (unset for real MSK, whose cert already chains to a public CA) — same self-signed-cert-pinning pattern already used for this project's `pi-remote-access` xpra direct-TLS setup, just applied to Kafka. Every machine publishing/consuming from a given broker needs these three fields set consistently in its own `.env`, same as `security_protocol`/`sasl_mechanism` already required per-machine overrides for a local PLAINTEXT broker.

   **`NoiseFloorDetector` is vectorized over a whole hop at once (`flag_hop(indices, powers)`), not called per-bin** — added 2026-08-16 after diagnosing a Raspberry Pi deployment pegging one CPU core at 100% with the producer backlogged (ping healthy, so not network-bound; confirmed compute-bound in the per-bin Python loop). Each channel's `n_bins`-wide rolling window (`KAFKA__BASELINE_WINDOW`, independent of `waterfall_rows`) is a circular-buffer 2D numpy array `(window, n_bins)` with per-bin `_fill_count`/`_cursor` arrays, replacing the old `dict[float, deque]`-per-bin design. Before calling `flag_hop`, each backend snaps the hop's real (possibly slightly off-grid) bin centers onto the channel's fixed grid via `nearest_grid_index(canonical_freqs, freqs)` (`np.searchsorted` + nearest-neighbor comparison) to get integer `indices` — real hardware's actual bin centers can differ from the nominal configured grid by sub-bin amounts, and `flag_hop` needs stable integer indices to index into its per-bin arrays. A bin only starts flagging once its own window has filled once (cold start, tracked per-bin via `_fill_count`). Measured ~9x faster than the old scalar per-bin loop at 20,000 bins/hop (realistic wide-HackRF-range scale): ~44ms → ~5ms.

   **Optional second, spatial check** (added to catch a whole band being uniformly noisy without treating that as N different signals — a single per-bin temporal baseline can't tell a genuinely elevated bin apart from a band that's just loud everywhere right now): if `spatial_margin_db` is configured (`kafka.rtl_spatial_margins_db`/`kafka.hackrf_spatial_margins_db` lookup, falling back to `kafka.spatial_margin_db`; `None` by default = disabled, pure temporal behavior), a temporally-flagged bin is only kept if it *also* beats that hop's median power (computed inside `flag_hop` itself via `np.median(powers)`, not by the caller) by that margin. It's an AND, not a replacement: spatial can only suppress an already-temporally-flagged bin, never flag one that failed the temporal check. **Optional third, prominence check** (added 2026-08-10, an OR alongside temporal rather than a refinement of it, unlike spatial): a signal that's always present and always strong — a steady FM broadcast carrier, say — trains straight into the temporal baseline and never looks "new" again no matter how strong it is, so temporal (and thus spatial, which only ever refines a temporal positive) never fires for it. If `prominence_margin_db` is configured (`kafka.rtl_prominence_margins_db`/`kafka.hackrf_prominence_margins_db` lookup, falling back to `kafka.prominence_margin_db`; `None` by default = disabled), a bin is flagged if it beats the hop's median by that margin **regardless of its own temporal history** — computed for bins not already flagged, so it's purely additive. Meant to use a bigger margin than `spatial_margin_db`, since a real narrowband peak clears a generous margin easily while generically noisy broadband bins (close to their own hop's median by definition) don't. All bins flagged within one hop are batched into a single JSON message (`streaming/kafka_publisher.build_payload()`) and published to one topic (`KAFKA__TOPIC`), keyed by channel label.

   **Optional periodic full keyframes** (`KAFKA__KEYFRAME_INTERVAL_S`, `None` by default = disabled): since the topic otherwise only ever carries flagged bins, a consumer with no live producer nearby (e.g. `kafka_viewer` on a different machine) sees permanent gaps everywhere except real signals — no noise-floor/baseline reference at all. Found live 2026-09-21 running `kafka_viewer` for real for the first time against a genuinely sparse topic. Each channel gets its own `streaming.detector.KeyframeScheduler` (built by `_build_keyframes()` in `sdr/__init__.py`, one per channel, same list-per-backend threading as `detectors`/`partitions`/`canonical_freqs`) — a trivial one-timestamp gate checked right alongside `flag_hop()`'s result at the exact same per-hop publish call site in every backend: if `keyframe.due()`, publish *every* bin of the current hop (not just the flagged ones) as an ordinary second `publisher.publish()` call, then `keyframe.mark_sent()`. No new message shape or consumer-side handling needed — `apply_message()`/`build_payload()` don't know or care whether a message came from flagging or a keyframe, since both are just "bins for this channel, snap and merge." A keyframe is scoped to whatever one hop already covers, not a synthesized full-channel-wide message: for `PlutoStareBackend` that's the whole fixed window in one shot (one capture already covers everything), while for RTL/HackRF/`PlutoBackend` sweep mode it's just that hop's own segment — the full channel's baseline still builds up naturally over one sweep cycle as each segment's own keyframe comes due in turn. Set the interval well above one real hop's duration, or every hop becomes a keyframe and the noise-floor filtering's whole point (cutting Kafka volume, see `STATS.md`) is defeated.

   **Partitioning is explicit, not left to Kafka's default key-hash partitioner**: `build_backend()` numbers every channel 0..N-1 in RTL-then-HackRF-then-Pluto order (mirroring `CompositeBackend`'s channel-list ordering) and passes each backend a parallel `partitions: list[int]` — the exact same shape/indexing convention as `detectors` — which `RTLBackend`/`HackRFBackend`/`PlutoBackend` thread through to `KafkaSignalPublisher.publish(..., partition=...)`, guaranteeing each channel's messages land on one fixed partition rather than hoping the key hash spreads them out. The topic must be provisioned with at least as many partitions as total channels. If `settings.kafka` is absent or `kafka.enabled` is false, none of this runs — `build_backend()` passes `publisher=None`/`detectors=None`/`partitions=None`/`canonical_freqs=None` and the per-hop detector/publish calls are skipped entirely.

All three backends share parsing and plotting code — subprocess command construction, edge-trimming strategy, and channel demuxing differ.

7. **Kafka viewer (`python -m freqscan.kafka_viewer`, `src/freqscan/kafka_viewer.py`)**: a read-only consumer that draws the same spectrum+waterfall plot from the Kafka topic instead of live hardware — for watching signals on a machine with no SDR attached. `KafkaConsumerBackend` (`streaming/kafka_consumer.py`) implements the same `SDRBackend` ABC as `RTLBackend`/`HackRFBackend`, so `plotting.run()` needs no changes beyond item 5's alignment fix to draw from it. `kafka_viewer.py`'s own `--plot-backend` CLI flag (`matplotlib`/`pyqtgraph`, mirroring `Settings.plot_backend`) picks the same rendering implementation independently of the producer's `.env`, since the viewer has no `Settings` of its own to read `PLOT_BACKEND` from (see Configuration above on `KafkaViewerSettings`). It uses `KafkaViewerSettings` (`config.py`), a small standalone settings class reading the same `KAFKA__*` `.env` vars as `KafkaSettings` but without going through `Settings`'/`_require_at_least_one_backend` (a viewer-only machine has no RTL/HackRF config at all).

   Channel layout comes from `KAFKA__METADATA_TOPIC` (default `freqscan.signals.metadata`), not from the signal messages: `build_backend()` (item 6) publishes one metadata message per channel, once at startup, on that channel's own partition — `{"channel", "freq_start_hz", "freq_stop_hz", "bin_width_hz", "n_bins", "run_epoch"}`, computed from static config (the same per-channel `ChannelGrid`s used for detector sizing, published via one shared `_publish_metadata()` in `sdr/__init__.py`; HackRF's `bin_width_hz` is `HackRFSettings.bin_width` — one value shared by every range, since `hackrf_sweep` only takes a single `-w` for its whole process; RTL's is per-device, `DeviceConfig.bin_width`). `KafkaConsumerBackend.__init__` blocks (up to `METADATA_TIMEOUT`, 10s, tracking per-partition `_PARTITION_EOF` to know when a partition has nothing more to offer) reading that topic from `OFFSET_BEGINNING` before doing anything else, printing `waiting for channel metadata...`/`got metadata for N channel(s)`.

   **`run_epoch` (`time.time()`, computed once per `build_backend()` call and reused for every channel's metadata message that run) exists because the metadata topic's partition count can only ever grow, never shrink** — once a topic has been provisioned/used for N channels, a later run with fewer channels (e.g. one HackRF range instead of three) still leaves the higher partitions holding their *previous* run's last message, since nothing ever deletes or compacts them. Deriving "how many channels this run has" from the broker's raw partition count (as an earlier version did) reads those stale leftover messages as real, live channels with old, wrong labels/extents — found live 2026-08-16 running with just 1 configured HackRF range against a locally over-provisioned 6-partition topic, and the viewer showed 6 channels with stale labels from an earlier, larger config. Fix: `KafkaConsumerBackend.__init__` reads metadata from every broker-reported partition as before, then keeps only the messages whose `run_epoch` equals the *maximum* `run_epoch` seen across all of them (exact equality, not a tolerance window — every message from one `build_backend()` call shares the identical value) — that's this run's live channel set, in contiguous partition order `0..n_channels-1`. A gap in that contiguous range (not all higher-numbered stale, but a genuine missing current-run partition) is `report_error()`, not a silent fallback. Only after this filtering does each channel's `state.sweep` get pre-populated with its **entire declared grid** (`np.linspace(freq_start_hz, freq_stop_hz, n_bins, endpoint=False)`) set to `NaN`, before the live signals consumer thread (seeked to `OFFSET_END`, as before) ever starts.

   This replaced an earlier "discover channels lazily from the first message per partition" design that had a real bug: since the signals topic only ever carries noise-floor-*flagged* bins (item 6), the known-bin set kept growing for a while after startup as new distinct frequencies got flagged for the first time — and because the waterfall's column positions depend on the *total* column count (item 5), that growth visibly reflowed the entire waterfall, not just new data, for a while after every startup. Publishing the true grid up front fixes this at the root instead of working around it in the rendering code.

   `apply_message()` merges a message's bins into `state.sweep` by **snapping each `freq_hz` to the nearest canonical grid frequency** (`nearest_grid_index()`, `np.searchsorted` + a nearest-neighbor comparison) rather than using it as a dict key directly — the producer's actual bin centers (parsed from `rtl_power`/`hackrf_sweep` output) and a grid computed from nominal config values can differ by sub-bin amounts, and without snapping that mismatch would silently add near-duplicate keys, reintroducing the exact growing-bin-count problem the metadata grid exists to avoid. Since metadata now provides labels/extents authoritatively before any real message arrives, `apply_message()` no longer does lazy label/extent discovery (a prior version did; removed as redundant, and it could have overwritten the correct full-range extent with a too-narrow one derived from just the first message's bins).

   Note the topic only carries noise-floor-*flagged* bins (plus periodic full keyframes if `KAFKA__KEYFRAME_INTERVAL_S` is set — see item 6), so the viewer's spectrum/waterfall are inherently sparser than the producer's own local plot (which sees every raw bin) unless keyframes are enabled — this is expected, not a bug.
